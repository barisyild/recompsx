# The runtime's and the backend's hottest variables in the SH-4's operand cache: "colour section",
# a colour being the variable's first line, mod 512, in the 16 KB direct-mapped operand cache.
# scripts/dc-layout.py place lists .data and .bss in full at every Dreamcast link with these first
# (scripts/build-dc.sh). Global: the same for every game, since the variables are the runtime's and
# the backend's, not a game's (docs/perf/dreamcast-ledger.md, E-007, E-022, E-043, E-058, E-069, E-100, E-107, E-109).
#
# Made 2026-10-03 (round r109, E-109; first E-100) by dc-ocache-sim dopt over three windows' operand
# traces — Crash 3's title screen and its gameplay demo, 20 M of 40 M accesses each, and Crash Bash's
# Ballistix window in all three of its phases (the match, a disc load at 19840, the scene after it at
# 20100: 14 M + 3 M + 3 M joined) — taken from builds with the code where it now is (each game's
# dc-placement.txt instruction colours of the same round, r109p1, the code of E-098..E-109), with the
# main stack at its start (backend_kos.c, 235 lines below the top of RAM): the 83 variables — the 80
# of E-107 and three a window now touches 10,000 times in 20 M (the pacer's next_deadline,
# TimeBase.perLine and Gpu.texPage, which GPUSTAT reads take: the disc load polls it ~2,900 times a
# vblank) — one colour each for every game, two rounds: each window's operand cost 0.892, 0.980 and
# 0.932 of its link's (the literal-pool halves were then chosen with these). Regenerate it the same
# way — after the code placements, from traces of a build that has them — when the hot variables
# change (out/_work/round3.sh in the session that made it; ledger E-100, E-108).
#
