# Dreamcast performance ledger

Everything tried to make the Dreamcast build faster: how it was measured, what it gave, and whether it
was kept. It exists so that nothing is tried twice by accident. **Read it before starting an
optimisation, and add a row when one is measured, kept or not.** A rejected idea stays here with its
numbers; retry it only when something it depended on has changed, and say what.

PROGRESS.md keeps the story and the log; this file keeps the ledger. Decisions that change how the
build works still get an ADR.

## The goal and where it stands

**Goal (owner, 2026-09-30):** Crash Bandicoot: Warped and Crash Bash run at full speed on the
Dreamcast, and every change that gets them there is global: it speeds up every game (the recompiler,
the runtime, the backend, the build), not one game's code.

**Full speed** is one emulated vblank per 16.7 ms: `Kernel.onFrame` presents at every vblank, and the
bench (`--dc-bench=FROM:TO`) reports ms per present. The judge is the cache model
(`scripts/dc-flycast-model.sh`), which read Crash 3's title screen within 1 % of a console; a result
worth keeping is confirmed on hardware (the tester, chap3l).

## How to measure

- **Build and run an experiment:** `scripts/dc-exp.sh <name> <base> <bench-data> [<cpp>]` (needs the
  KOS environment). It builds `out/_x_<name>` from `out/<base>`'s generated code (or another
  transpiled tree for a runtime change), makes a bench GDI and runs the model; several can run at
  once. Flags: `DC_EXTRA_FLAGS="..."`. Traces: `MODEL_VARS="RXTRACE=n RXOTRACE=n"`.
  - Crash 3: base `_c3time`, bench data `out/dc/c3data-tbench` (3300:4050), ~5 min of model.
  - Crash Bash: base `_cbpl` (mods onlinemenu,mouse), bench data `out/dc/cbdata-plbench`
    (18800:20300), ~15 min of model.
- **Read it:** `scripts/dc-prof.py <prof> <elf> --frames N` prints the frame and its parts; add
  `--top N`, `--hot FUNC`, `--lines FUNC` (by source line), `--annotate FUNC` (every instruction with its
  samples). `scripts/dc-cmp.py <exp> [<exp-b>]` gives one experiment by part, or the conflict-free change
  from one to another by part and by function.
- **The hardware path's output, in seconds:** `node <game.js> <exe> <bin> --video-hw --gpu-hash N` hashes
  every call the runtime makes to the backend (the JavaScript shim, the same FNV and seed as the null
  backend's `--gpu-hash`, so both targets print the same hash; `--gpu-hash-frames`, `--gpu-hash-trace N`
  find where two runs part). Crash 3, `out/dc/c3data-tbench`, 4050: `5f877994a1335867` over 3,098,753
  calls (JS and C++); Crash Bash with its mods, `out/dc/cbdata-plbench`, 20300: `07076c3751a9d204` over
  14,472,953 (JS). A change to polygonHw, the list walk or the backend's inputs keeps these. `scripts/dc-mix.py <prof> <elf> [regex] [--pool]` gives the sampled time
  by kind of instruction.
- **A placement round with the data colours** (E-100): after the code colours and p1 (builds with
  `RXOTRACE=40000000`), `dc-ocache-sim stat <otrace> <objects> 20 <counts>` for each window, the items
  being every variable of `src/backend/dreamcast/dc-data-placement.txt` still linked plus every other
  `.data`/`.bss` object a window touches 10,000 times in its 20 M; then `dc-ocache-sim dopt <items> <all>
  2 20000000 <out> 8cff0000 0` over the three windows' traces at once (~30 min: each colour of each
  item replays all three), the halves with the result, and p2 with both: `scripts/build-dc.sh ...
  --data-placement <candidate>` links with a candidate before it replaces the repo's file. The
  session's driver was out/_work/round2.sh. A code change that moves much code wants a new round:
  E-101 and E-102 were judged on r99's placements, and both moved the layout they were judged on.
- **Every phase of a window in its traces** (E-108): a trace starts at the bench's first present, and
  24 M instruction entries are ~100 of Ballistix's frames — its window is the match, a disc load at
  19840 and the scene after it at 20100, so each gets a bench image of its own (out/dc/cbdata-ldbench,
  cbdata-pbbench) and a share of the joined trace (out/_work/round3.sh: CBI, CBO, and CBK, the
  sections placed). The bench's "slow presents" line names the presents over 33.4 ms; JavaScript says
  what ran in them (a per-function instruction count in a scratch copy of the generated tree).
- **The recording ends before the report** (E-108): `@@rxprof stop` comes before the bench's lines,
  which had been ~900 characters of serial output inside the profile — 0.128 ms of each of a 300-frame
  window's frames. Frames before E-108 carry it (gameplay 0.13, title 0.05, Ballistix 0.03 ms).
- **Windows of play past the title, by a scripted pad** (E-130, E-132): `--pad-script F:B,F:B,...`
  (`sio.PadScript`; every game and target) plays pad 0 from vblank F on — Crash 3's START at 3400
  begins a new game, whose intro runs the dark Uka Uka scene at ~6750-10000 and arrives in the warp
  room at ~14500. Bench discs with it: out/dc/c3data-uka (6750:7050) and c3data-warp (15000:15300);
  JavaScript's digests with that script a0b9d5bc at 7050 and f4e397b8 at 15300
  (`DIGEST_ARGS=$'--pad-script\n3400:START,3410:-' scripts/dc-digest.sh ...` for the console
  build's). Without a script a bench run's pad 0 is the model Flycast's default controller and
  JavaScript's is unplugged; the two follow the same frames all the same (a JS count with pad 0
  plugged and idle, `--pad-script 0:-`, equals the unplugged one).
- **Which scene a present is** (E-132): `RXPROF_SHOTS=<dir>` makes the profiling Flycast save a
  picture at each `@@rxprof shot pNNNNN` the bench disc prints (every 150 presents); a run with
  `RXCACHE=0` gets to Crash 3's 15000 in ~7 min (out/_work/shots.sh). The JavaScript side:
  `--vram-at F,F,...` writes vram-F.bin (1024x512 halfwords) at those frames.
- **The first window of a batch has the bare name** (placed.sh and the rounds): `out/_x_<name>` is the
  first bench disc given — the title's in every round so far — and `<name>w1`, `w2`... the next ones;
  read the window off the prof.log's bench line before reading a profile.
- **A paced window's total cannot go under 16.68 ms**: time the emulation saves is spent waiting for
  the next vblank (`idle`, the pacer). Judge a change by `work` (conflict-free less idle) and by the
  presents over two frames' worth, not by the total alone.
- **The scene build's output, exactly:** a build with `DC_EXTRA_FLAGS=-DRECOMPSX_TA_HASH=1` hashes
  every header and vertex `build_scene` sends the TA, eight words each in order (dc_internal.h's
  `TA_HASH`), and logs `ta hash <scene> <hash>` a scene to prof.log. Nothing in a present depends
  on the host's time, so two builds that send the PVR the same scenes log the same lines: a change to
  the scene build is checked by one hash build of the code before it and one after, over the same
  windows (Crash 3's two: 1,889 and 2,170 scenes from boot; Crash Bash's Ballistix: 7,974). Not for
  timing: the hash costs as much as the build. Build the two **one after the other, with
  `--no-placement --no-data-placement` and nothing else building**: a placed build links twice, and
  its second link is a full ninja run that compiles whatever the tree's file is by then — a file
  swapped back after the first compile ends up in the "before" build too.
- **Compare code changes on the conflict-free time**, never on the frame alone. Placement (ADR-0043)
  is tuned to one build's code: change the code and the hot lines move inside their functions, and the
  instruction conflicts come back (E-002 read 32.7 ms for a change that was neutral). The
  conflict-free time is the frame less both conflict columns: what it would be with every conflict
  placed away. A change that is good there is then placed again (a new trace and `opt`) before the
  frame is judged.
- **Layout changes** (placement, stack, data) are judged on the frame itself, with the code unchanged.
- **The model's version matters** (E-015): v2 (2026-09-30) charges write-backs and store-queue bursts
  to their instructions and takes conflict write-backs out of the conflict-free time. Compare v2
  runs with v2 runs; to compare with an older experiment, run it again (`DC_EXP_REUSE=1
  scripts/dc-exp.sh <name> ...` measures the build already in out/_x_<name>).
- **Idle is not work.** Where a present is ahead of its vblank, `bp_pace_frame` sleeps and KOS's
  idle thread runs: Crash Bash's bench spends 1.3 ms a frame there even at 24-27 ms a frame (its
  presents are uneven, and the pacer's debt is capped at four frames). `dc-prof.py --frames` prints
  it as `idle` and the conflict-free time less it as `work`; compare `work`.
- **Memory is a limit, not a detail.** The loaded image, the heap and the stack share 16 MB: Crash
  Bash with its mods needs about 3.6 MB of heap, and a 13.07 MB image ran out at boot (E-014). Read
  `loaded image` in every experiment's output; anything that grows code must say what it costs.
- **A path's cost without the caches, in seconds:** `scripts/dc-issue-sim.py` replays the model's
  issue rule (pairing by unit) and operand scoreboard over one path through a function — of a built
  object, the branches named (`--path tnn...`), or of a model run, the way its counts went
  (`--counted`). GCC's `cmdRtps` replayed: 233 cycles, the model measured 232 (E-080). For timing a
  form of the code before building it.
- **Caches offline:** `scripts/dc-icache-sim.c` replays an instruction trace (`RXTRACE`) against a
  placement of the code; `scripts/dc-ocache-sim.c` replays an operand trace (`RXOTRACE`: every
  operand access, whole address) by object (`stat`), for every start of the stack (`stack`), and
  searches colours for data objects over several games at once (`dopt`). Objects come from
  `scripts/dc-layout.py objects <map>`.
- Flycast's own timing (`dc-flycast-prof.sh`) models no cache and no stall. Numbers from it before
  2026-09-28 are CPU-work comparisons only.
- **The game digest on the Dreamcast** (`scripts/dc-digest.sh <elf> <data> <frames>`, 2026-10-03): the
  build runs headless under the model's Flycast build and prints GenMain's digest, the one JavaScript
  prints for the same frame — so the Dreamcast build is held to the reference, not only to another
  Dreamcast build. Headless means the software rasteriser and no sound: the generated code, the
  runtime and the RTPS core are checked, the polygon core and the scene build are the TA hash's. The
  r117 builds (5fa9442's code and E-113/E-114/E-117): Crash 3 at 5000 **47853ef7** and Crash Bash (its
  mods in) at 20300 **95e17b07** — JavaScript's both (Crash 3 930 s with the cache model on; Crash Bash
  ~32 min with `RXCACHE=0`, the default).

## Where the time goes (2026-10-03, after E-119)

Crash 3's gameplay on r117p2 (the r117 CDIs' code), a frame under the model: 24.86 ms — issue 11.63,
instruction fills that are not conflicts 6.14, operand fills that are not conflicts 1.72, dependencies
2.49, conflicts 2.35. Counts from RXCOUNT (`.cache.count`); guest memory from a JavaScript build with
counters (vblanks 4700-5000; Crash Bash 18800-20300).

- **Generated code:** 1.34 M SH-4 instructions a frame in 5,203 calls (270 a call). By form: literal-pool
  loads 178 K (13.3 %), displacement loads and stores 293 K (21.9 %; ~270 K of them CpuState, the rest
  span accesses within 60 bytes), indexed 17 K, pushes and pops 33 K.
- **Literal pools miss in the operand cache:** the generated code's pool loads took 8,263 fills a frame
  (0.99 ms; a fully associative cache 3,909), the rest's 3,387 (0.41 ms) — a pool line is one more line
  per function, cold each time the function's code is. By constant (generated code): 16-bit constants
  46 K loads / 3,552 fills (span offsets past 60 bytes and immediates past 8 bits; GCC never builds one
  from `mov #imm` and a shift), the memory map's (masks, the arena's and the scratchpad's addresses)
  98 K / 2,688, other 32-bit 18 K / 1,088, addresses 7 K / 722, the GTE file 9 K / 214.
- **Far branches:** 6.4 K `braf` a frame in generated code (f_80038e28 3,007 of them; every target
  4 KB or more away, past `bra`'s reach), each reading its offset word, which sits in the code, through
  the operand cache: 2,004 fills a frame (0.24 ms).
- **Instruction lines:** the generated code fills 34,056 lines a frame (4.1 ms); of their slots 69.3 % ever
  run in the window, 15.0 % are cold code, 7.4 % literal pools, ~7 % trampolines and their delay slots.
  The rest of the program: 22,375 lines, 80.2 % run.
- **Guest memory:** Crash 3 57 K accesses a frame, 41 % to the scratchpad; unspanned RAM 12.7 K,
  scratchpad 3.4 K, ports 0.55 K; span set-ups 10.6 K a frame — 6.2 K RAM (~8 instructions), 4.3 K
  scratchpad (~22: the RAM test first, then the scratchpad's, six pool constants). Crash Bash: unspanned
  RAM 6.5 K, scratchpad 1.3 K, ports 1.1 K; set-ups 4.6 K RAM, 0.5 K scratchpad, 0.1 K none. Testing
  the scratchpad first for a non-negative base would save Crash 3 ~31 K instructions a frame and cost
  Crash Bash ~4 K: not global.
- **State machines:** the 45 functions the structurer leaves as `while (true) switch (bb)` take 1.37 ms
  of the generated code's conflict-free time; f_80038e28 0.70 (49 KB of SH-4 for 1,454 MIPS
  instructions, 32 calls a frame).
- **Audio:** the SPU's batch (`Scheduler.fireRest`, 0.24 ms) counts its due samples one subtraction
  at a time (~6.7 K instructions a frame) and checks 24 voices for the backend at every batch.

Each item above is the C compiler's way with this code on the SH-4: no one of them moves more than
~0.3 ms in place. Together — pools, CpuState traffic, decode constants, cold slots in hot lines — they
are what a code generator holding the memory map's constants and the hot guest registers in SH-4
registers would not produce (PROGRESS.md, Blockers 2026-10-03, option 1).

- **What is left of the guest memory path** (measured on E-112's gameplay, time by construct):
  unspanned decode 13.6 % of the generated code's time (1.67 ms; spread over many base registers —
  a3, s4+652, a0, t8+320 … — none above 8 %; the scratchpad path pays the RAM test first), span
  tests 9.3 %, span set-up 7.4 % (each function's entry: ~12 instructions and three pool constants a
  span). No item here is above ~0.2 ms without changing how spans are proved.
- **`unwindToken` as a return value:** each guest call is followed by a load of `ctx.unwindToken`
  and a test (1.9 % of the generated code's time with its fills); returned in r0 it is a test:
  ~−0.1 ms.
- **The scratchpad's span:** ~3,200 of Crash 3's span set-ups a frame have a base of exactly
  1F800000h and pay the RAM test first (~22 instructions, six pool constants, where RAM's take ~8).
  Testing the scratchpad first by the base's sign gains Crash 3 ~31 K instructions a frame and costs
  Crash Bash ~4 K; a hint from the callers (E-121) finds nothing hot. Left for a code generator that
  knows the base (ADR-0048).
- **The brightening header per state** (g_sres): `over_header` 119 times a frame, ~94 instructions
  each through emit_header's cache: ~−0.04 ms; not in Crash Bash's top sixty functions either.
- **The DMA list walk's events:** ~170 a frame (E-039), each a pump, the walk's own setup and, in
  generated code, every live span taken again: ~0.3 ms. Coarser stretches (LIST_STEP) change what a
  game sees (ADR-0039: Crash Bash's pause-menu text); cheaper events do not.
- **Diagnostic counters:** `wordsReceived`/`commandsReceived` are in the game digests (GenMain) and
  stay exact; `Gpu.opCount` is read only by the frame dump at vblank 8000 (Kernel.reportOpcodes),
  and its increment is ~5.6 K instructions a frame in the list walk alone (~0.03 ms).
- **Brightened and subtractive passes batched** across a run of primitives that do not overlap:
  Crash Bash brightens 341 triangles a frame, each two header switches and the run broken; needs a
  pixel-exact non-overlap test, since the second pass of one must not land on the first of the next.
- **Architectural** (PROGRESS.md, Blockers 2026-10-03; each an ADR and the owner's decision): guest
  code generated for the SH-4 directly (ADR-0048: the generated code's ~10.7 ms toward ~6-7), the scene
  straight to the PVR (~0.7-1.5 ms), guest RAM through the MMU (~2-3 ms, not measurable on the model);
  even the first alone would leave gameplay near 20-21 ms.
- **Frame skipping** is not full speed and is a last resort.
